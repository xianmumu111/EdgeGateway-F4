### 第 1 项：为什么必须改

```
[RPT][S0] TX: 01 03 00 00 00 02 C4 0B[RPT][S0] RX: 01 03 04 ...
                                      ↑ 粘一行了
```
RX 那行有 `\r\n`，TX 那行没有。补上就行。

### 第 2 项：不是 bug，是定时炸弹

```c
if(osMessageQueuePut(s_q_sample,&s,0U,0U) != osOK)
s_dropped++;
```

**语义是对的**（`if` 不带括号只管紧随的一条语句），但缩进写成同一级，
以后你想在 if 里加一行 `uprintf("drop\r\n")`，**它会在每次循环都执行**。
加括号：

```c
if (osMessageQueuePut(s_q_sample, &s, 0U, 0U) != osOK) {
    s_dropped++;
}
```

### 第 3 项：顺手的清理

`defaultTask` 是 CubeMX 默认生成的空任务（`for(;;) osDelay(1);`），
优先级 `osPriorityNormal` **比 `taskModbus`（BelowNormal）还高**。
现在无害（它有 `osDelay`），但留着是个说不清的东西。删掉。

> 可选：`.ioc` 里 FreeRTOS 的 `configMAX_PRIORITIES` 默认是 **56**，
> 你一共 3 个任务。FreeRTOS 找最高优先级就绪任务要扫这个数，
> 56 会让它每次调度多花时间。改成 **8** 能覆盖到 `osPriorityRealtime`，
> 调度更快。这是面试能讲的一条优化，但**今天不做也行**，别在主线里掺。

## 2. 今天主线：把波特率从 9600 提到 115200，看整套链路还成不成立

### 为什么是这个

- **不需要任何新硬件**（RS485 模块、SD 卡、ESP 都还没到）
- 你现在的分帧判据全是在 9600 下验证的。**没被别的条件验过的东西，不能说它成立**
- 高波特率会同时打到三个地方：从站 t3.5 判据、主站 IDLE 分帧、`HAL_GetTick()` 的精度

### ★ 我预计你会撞到的坑（先看，别蒙着头改）

**从站的 t3.5 判据在高波特率下会失效。**

`nodes/f103_slave/Core/Src/modbus_slave.c:36-40`：

```c
#if MODBUS_BAUD > 19200
#define MODBUS_T35_MS  2          /* 固定 2ms */
#else
#define MODBUS_T35_MS  ((35000UL / MODBUS_BAUD) + 1)   /* 9600 下 = 4ms */
#endif
```

而判据在 `modbus_slave.c:125`：

```c
if ((uint32_t)(HAL_GetTick() - last_rx_tick) < MODBUS_T35_MS)
```

**`HAL_GetTick()` 是毫秒分辨率。** 115200 下：

| 量 | 值 |
|---|---|
| 1 个字符 | **86.8 µs** |
| 3.5 字符（理论） | **304 µs** |
| 规范规定（>19200 固定） | **1750 µs** |
| 你现在的宏 | 2 ms |
| `HAL_GetTick()` 分辨率 | **1000 µs** |

⇒ 用 1ms 精度的尺子去量 1.75ms 的间隔，**误差能到 57%**。
表现出来就是：偶尔把一帧切成两半，或者两帧之间等太久。

### ⚠️ 顺带纠正我 9/17 说错的一句话

我 9/17 记的是「2ms 偏激进，现场长帧可能误判帧结束」。**这句说反了。**
2ms > 1750µs，等得**更久**，是**保守**方向，不会误判帧结束；
代价只是每帧多等 0.25ms，且**不符合规范**。
真正危险的是 t3.5 设得**太小**。认错。

现在跑的是 9600，走 else 分支（4ms），**高波特率那个分支根本没被执行过** ——
这也是今天要做这个实验的理由之一：**没跑过的代码路径，不算数。**

# 3. 实测结果（2026-09-19 17:05 全部收齐）

## 3.1 三档波特率，五步全通，帧字节**逐字节一致**

```
S0 TX 01 03 00 00 00 02 C4 0B   RX 01 03 04 00 64 00 C8 BA 7A
S1 TX 01 06 00 04 03 7F 89 1B   RX 01 06 00 04 03 7F 89 1B
S2 TX 01 03 00 04 00 01 C5 CB   RX 01 03 02 03 7F F9 54
S3 TX 01 03 00 C8 00 01 05 F4   RX 01 83 02 C0 F1      ← 异常帧 5 字节
S4 TX 02 03 00 00 00 01 84 39   RX（无）
```

9600 → 38400 → 115200 **三档下这 9 帧一个字节都没变**。通信链路全程无丢字节、无 CRC 错。

| 步 | 9600 (ms) | 38400 (µs) | **115200 (µs)** |
|---|---|---|---|
| S0 | 23 | 6524 | **3368** |
| S1 | 22 | 6227 | **3267** |
| S2 | 21 | 5982 | **3192** |
| S3 | 19 | 5477 | **3013** |
| **S4** | **208** | **201351** | **200352** |

**S4 全程不动** —— 200ms 是软件超时，跟波特率无关。这条从一开始就预判对了。

## 3.2 ★ 耗时模型：跨波特率成立，误差 <1%

```
elapsed = (tx_len + rx_len) × 字符时间 + t3.5 + IDLE(1字符) + 软件开销
```

| 量 | 38400 | 115200 |
|---|---|---|
| 1 字符 | 260.417 µs | 86.806 µs |
| t3.5（规范 >19200 固定） | 1750 µs | 1750 µs |
| 软件开销（实测反推） | +70.7 µs | +49 µs |

**关键：模型参数全部来自 38400 的数据，没有用 115200 重新拟合。**

| 步 | 115200 预测 | 115200 实测 | 残差 | 误差 |
|---|---|---|---|---|
| S0 | 3383 | 3368 | −15 | **0.45%** |
| S1 | 3296 | 3267 | −29 | **0.90%** |
| S2 | 3210 | 3192 | −18 | **0.55%** |
| S3 | 3036 | 3013 | −23 | **0.76%** |

> **在一个波特率上拟合、在另一个波特率上验证** —— 这才叫模型成立。
> 拿同一批数据既拟合又验证，那叫过拟合。

### ★ 用残差符号反推代码改动是否生效（不用问，数据自己说）

拿两种 t3.5 假设分别套 38400 的数据：

| 假设 | 残差范围 | 结论 |
|---|---|---|
| t3.5 = **1750 µs** | **+50 ~ +87**，全为正 | ✅ 成立（软件开销不可能为负） |
| t3.5 = 2000 µs | −163 ~ −200，全为负 | ❌ **假设被推翻** |

⇒ 从站 t3.5 已确从 2ms 改成 1750µs。后查 `modbus_slave.c:39` = `MODBUS_T35_US 1750UL`，**反推与源码互证**。

## 3.3 ★★ 系统瓶颈分析（面试讲这段）

波特率 38400 → 115200 = **3.00 倍**，但实测只快了 **1.9 倍**。账在这里：

| | 38400 | 115200 | 变快 |
|---|---|---|---|
| 线路传输（17 字符） | 4427 µs | 1476 µs | **3.00x** ✅ |
| 固定开销（t3.5 + IDLE + 软件） | 2097 µs | 1892 µs | **1.11x** ❌ |

**固定开销占比：38400 时 32% → 115200 时 56%。**

```
波特率提上去之后，瓶颈从"线路"转移到了"协议等待"。
t3.5 = 1750µs 是协议规定的死重，不随波特率变小，而且是规范下限不能动。
⇒ 这就是阿姆达尔定律的现场版：
   你优化了一个只占 68% 的部分，剩下 32% 纹丝不动，
   整体收益必然达不到理论倍数。
```

**所以"再往上提波特率"在 >19200 之后收益递减。** 真正要提速得换思路：
合并寄存器到一帧、减少轮询点、广播 + 异常上报。这个等 CP1 接真实变送器时再展开。

## 3.4 ms 尺子 vs µs 尺子（DWT 的价值实测）

| | 38400 下 S0/S1/S2/S3 |
|---|---|
| `HAL_GetTick()` 读到的 | 6 / 6 / 6 / 5 ms ← **全一样，看不出差别** |
| DWT 读到的 | 6524 / 6227 / 5982 / 5477 µs ← **差得清清楚楚** |

相邻差实测 **297 / 245 / 505 µs**，理论 **260.4 / 260.4 / 520.8 µs**。
尤其 S2→S3 少 2 个字符：115200 下实测差 **179 µs**，理论 173.6 µs。

## 3.5 115200 下的两个风险点（实测未触发，但要知道）

1. **主站 IDLE 阈值只剩 86.8 µs**（1 字符）。从站发响应时字节间被打断超过这个值，
   DMA 的 IDLE 会中途触发。但因为主站靠 `mb_master_rsp_len` 预判长度从 ringbuf 取，
   **不靠 IDLE 分帧**，所以不会拆错帧 —— 前提是 `RxEventCallback` 每次都正确写入 ringbuf 并重启 DMA。
   **本次实测等于压过了这条路径。**
2. **从站是中断逐字节接收**，115200 下每 86.8 µs 进一次中断。F103@72MHz 处理一次约 1~2 µs，
   占用率不高；t3.5 = 1750 µs 的容忍度也足够。

⚠️ 以上都是 **TTL 直连**下的结论。现场 RS485 差分 + 长线，115200 需重新验证。
